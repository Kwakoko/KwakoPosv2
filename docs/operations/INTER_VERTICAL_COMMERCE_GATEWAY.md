# KwakoPos Inter-Vertical Commerce Gateway

## Purpose

The gateway connects a buyer business (for example, Retail in Mwanza) to a seller business (for example, Wholesale in Dar es Salaam). The two remain separate tenants. The gateway shares only order, product-snapshot, fulfillment, and settlement information authorized by an accepted connection; it does not grant either tenant direct access to the other tenant's ordinary API or database scope.

## Deployment

1. Apply the Prisma migration named 202610090001_inter_vertical_commerce_gateway.
2. Deploy the API with interVerticalCommerceRoutes registered.
3. Confirm GET /api/v1/inter-vertical/health reports PostgreSQL persistence.
4. Use an authenticated tenant/branch context and the expected business permissions.
5. When a seller accepts a connection, it must provide a positive creditLimit in TZS. This becomes the seller's local B2B customer credit limit and is rechecked at dispatch. The seller can adjust that local customer's credit limit through normal customer management.

The API can lazily create these tables in a new environment with CREATE TABLE IF NOT EXISTS; applying the migration remains the required deployment path.

## Business workflow

PENDING CONNECTION → ACTIVE CONNECTION → SUBMITTED ORDER → ACCEPTED / REJECTED → DISPATCHED → IN TRANSIT → PARTIALLY RECEIVED / RECEIVED → PAYMENT SUBMITTED → SETTLED

Partial dispatches, receipts, and payments are supported. The seller must confirm a reported payment before matched native payment records are posted to both businesses.

## Main API routes

| Method | Path | Purpose |
|---|---|---|
| GET | /api/v1/inter-vertical/health | Gateway health |
| GET | /api/v1/inter-vertical/connections | Connections visible to the authenticated branch |
| POST | /api/v1/inter-vertical/connections | Buyer requests a connection to a seller tenant |
| POST | /api/v1/inter-vertical/connections/:id/respond | Seller accepts or rejects; ACCEPT requires a positive creditLimit |
| GET | /api/v1/inter-vertical/catalog?connectionId=... | Buyer browses the connected seller's active-branch catalog |
| POST | /api/v1/inter-vertical/orders | Buyer submits a purchase request |
| GET | /api/v1/inter-vertical/orders?role=buyer%7Cseller&status=... | List orders for authenticated tenant and branch |
| GET | /api/v1/inter-vertical/orders/:id | Order plus event/payment history, only for a participating branch |
| POST | /api/v1/inter-vertical/orders/:id/respond | Seller accepts with quantities/prices or rejects |
| POST | /api/v1/inter-vertical/orders/:id/cancel | Buyer cancels before dispatch |
| POST | /api/v1/inter-vertical/orders/:id/dispatch | Seller records stock-out, Sale, CustomerInvoice and GL journal |
| POST | /api/v1/inter-vertical/orders/:id/in-transit | Seller records carrier, tracking number and ETA; advances persisted inbound shipments |
| GET | /api/v1/supply-chain/shipments | List shipments for the authenticated receiving tenant/branch |
| GET | /api/v1/supply-chain/shipments/:id | Read shipment lines and lifecycle audit events within the receiving tenant/branch |
| POST | /api/v1/supply-chain/shipments | Create a persisted shipment for an eligible native Purchase Order |
| POST | /api/v1/supply-chain/shipments/:id/status | Apply an allowed shipment status transition with an idempotency key |
| POST | /api/v1/inter-vertical/orders/:id/receive | Buyer records receipt, stock-in, AP balance and GL journal |
| POST | /api/v1/inter-vertical/orders/:id/payments | Buyer submits a payment claim for seller confirmation |
| POST | /api/v1/inter-vertical/orders/:id/payments/:paymentId/confirm | Seller confirms payment; posts matched AP and AR payments/journals atomically |
| GET | /api/v1/inter-vertical/orders/:id/events | Lifecycle audit trail, tenant-scoped |

Every create/mutate request must include an idempotencyKey generated by the client (8–200 characters). Requests must use the existing KwakoPos authenticated session; clients must not supply or override the acting tenant or branch ID.

## Example: request a connection

POST /api/v1/inter-vertical/connections

    {
      "sellerTenantId": "REGISTERED-WHOLESALER-TENANT-ID",
      "notes": "Retail branch in Mwanza requests wholesale supply",
      "idempotencyKey": "mw-retail-link-2026-10-09"
    }

The seller accepts the request from the branch that will fulfill orders:

POST /api/v1/inter-vertical/connections/:id/respond

    {
      "action": "ACCEPT",
      "creditLimit": 5000000,
      "idempotencyKey": "wholesale-accept-2026-10-09"
    }

## Example: submit an order

Call the catalog endpoint first to get valid sellerVariantId values. Every order line must map to an active Retail variant, either by supplying buyerVariantId or by accepting the gateway's exact-SKU match. If a Retail variant does not exist yet, create it in Retail inventory before submitting the order. The gateway creates a native Retail PurchaseOrder in DRAFT status at submission, then updates it to APPROVED with the accepted wholesale quantities and prices when the seller accepts; receipts are linked to that same native PO.

POST /api/v1/inter-vertical/orders

    {
      "connectionId": "CONNECTION-ID",
      "currency": "TZS",
      "notes": "Replenishment for Mwanza branch",
      "idempotencyKey": "mw-order-2026-10-09-001",
      "items": [
        { "sellerVariantId": "WHOLESALER-VARIANT-ID", "buyerVariantId": "RETAIL-VARIANT-ID", "quantity": 24 }
      ]
    }

## Example: seller acceptance

The seller can confirm order quantities. Omitted lines use requested quantities. Pricing is resolved server-side through the existing PricingAuthority, including customer-specific prices, promotions, wholesale tiers, bulk tiers and price lists. A supplied override price is accepted only when the normal price-override permissions and a reason are present. A seller must have enough remaining B2B customer credit for the accepted total.

POST /api/v1/inter-vertical/orders/:id/respond

    {
      "action": "ACCEPT",
      "idempotencyKey": "wh-accept-order-2026-10-09-001",
      "items": [
        { "lineId": "ORDER-LINE-ID", "quantity": 24, "unitPrice": 12500 }
      ]
    }

## Example: dispatch and receipt

Seller dispatch:

POST /api/v1/inter-vertical/orders/:id/dispatch

    {
      "idempotencyKey": "wh-dispatch-2026-10-09-001",
      "carrierName": "Line-haul transport",
      "trackingNumber": "TRK-001",
      "items": [{ "lineId": "ORDER-LINE-ID", "quantity": 24 }]
    }

Buyer receipt:

POST /api/v1/inter-vertical/orders/:id/receive

    {
      "idempotencyKey": "mw-receive-2026-10-09-001",
      "notes": "Counted at Mwanza branch",
      "items": [{ "lineId": "ORDER-LINE-ID", "buyerVariantId": "RETAIL-VARIANT-ID", "quantity": 24 }]
    }

## Implementation notes and current limitations

- Product variants are tenant/branch-owned; seller IDs are never used as buyer inventory IDs.
- Dispatch locks seller stock and the linked Retail PurchaseOrder, checks authoritative stock-ledger balance, writes immutable stock-ledger movements, and refreshes stock projections.
- Seller dispatch creates a native Sale, CustomerInvoice, accounts-receivable balance, and general-ledger journal. Dispatch is blocked if it would exceed the configured B2B customer credit limit.
- Each gateway order is linked to a native Retail PurchaseOrder exposed to the existing purchasing module. Seller acceptance updates accepted quantity/authoritative price and PO status; goods receipts link to the PO and update its partial/complete receipt status. Buyer receipt also creates a native PurchaseReceipt and SupplierInvoice, stock-ledger movements, supplier payable balance, invoice allocations, and a general-ledger journal. Receipt totals are reconciled against the exact per-dispatch invoice tax/amount snapshot.
- Each dispatch creates a PostgreSQL-persisted inbound shipment in the buyer tenant/branch, linked to the native PO, gateway order, supplier mapping and shipment lines. Transit updates shipment tracking/status; receipt updates shipment line quantities, actual arrival and completion status. Shipment events are idempotent and tenant/branch scoped. The legacy in-memory supply-chain engine is not used as production shipment authority.
- Payment requests do not modify balances. Seller confirmation writes buyer supplier payment and seller customer payment records, updates payable/receivable balances and invoice allocation, and writes both journals in a single database transaction.
- Shipment tracking is stored in the gateway logistics snapshot in this first iteration; it does not create a record in the separate supply-chain shipment subsystem.
- Settlement request methods currently support bank transfer and mobile money only, because those can be reconciled without bypassing cash-session controls. Cash, card and other methods are intentionally not exposed in this gateway flow.
- Seller invoices resolve the same authoritative branch `tax.config` and active Tax record used by the existing commercial sale path. The resolved tax rate/inclusive mode is stored on Sale and CustomerInvoice lines and used in the invoice totals. When the seller branch has TRA VFD enabled, the fiscalization record and durable TRA outbox item are written in the same database transaction as the invoice; the existing worker handles submission, retries and reconciliation. When TRA VFD is disabled, invoice creation does not falsely report a fiscal receipt as issued.
- Buyer receiving preserves the seller-invoice tax snapshot on native SupplierInvoice lines. If the buyer branch has VAT enabled, recoverable input VAT is posted separately from inventory in the purchase journal; otherwise the gross received cost is capitalized. Confirm each business's VAT registration/tax settings and the seller's TRA VFD credentials/configuration before production use.
- Mutations require the appropriate business permissions or an authorized managerial role.
